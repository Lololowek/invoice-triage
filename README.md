# invoice-triage

Загружаешь PDF счёта, система извлекает поля по схеме, подсвечивает те, которым нельзя доверять,
человек правит, правки логируются и становятся материалом для замера качества.

> Статус: готово ядро — схема, кандидаты, клиент модели, сопоставление, три слоя проверки,
> политика риска, генератор 15 счетов с эталоном, консольный прогон. В работе: API, хранилище,
> журнал правок, тесты и CI, фронт, замер качества. Сквозной прогон на настоящей модели ещё не
> сделан: в среде разработки модели не было, путь проверен подставным клиентом (см. «Статус»).

## Какую задачу решает и почему это проблема

Извлечь поля из счёта умеет любая современная модель. Трудно другое — понять, **какие из
извлечённых полей можно принять без человека**. Если проверять всё, автоматизация бесполезна.
Если не проверять ничего, однажды деньги уйдут не на тот счёт.

Спрашивать модель «насколько ты уверена» бессмысленно: самооценка модели не откалибрована, и
выдуманный номер договора она возвращает с той же уверенностью, что и настоящий. Поэтому решение
«показать поле человеку» принимается по **объективным проверкам**, которые не зависят от модели.

## Архитектура: модель выбирает, а не пишет

Модели не дают документ со словами «заполни схему». Поиск значений и их сопоставление полям
разделены:

```
PDF ─► текст ─► кандидаты ─► модель: поле → id кандидата ─► проверки ─► политика риска
       pdfplumber   регулярки,        (сопоставление)          3 слоя       что показать
                    без модели
```

1. **Кандидаты** (`src/triage/candidates/`). Обычный Python проходит по тексту и собирает все даты,
   суммы, идентификаторы (БИН/ИИН, ИНН, VAT, IBAN, BIC, БИК, р/с, номера документов) и валюты. У
   каждого кандидата есть id, тип, исходная подстрока, нормализованное значение и позиция в тексте:
   ```
   D1  date        2026-01-15      '15.01.2026'
   A9  amount      47000.00        '47 000,00'
   I5  identifier  131144394289    '131144394289'   bin_iin,inn
   ```
2. **Сопоставление** (`src/triage/llm/`). Модель получает текст с метками
   `22.01.2026[[D1]]`, список кандидатов и описание полей. Возвращает она **не значения, а id**:
   ```json
   {"issue_date": {"candidate": "D1", "quote": null, "value": null},
    "contract_number": {"candidate": null, "quote": null, "value": null}}
   ```
3. **Выводимые поля** (категория расхода, признак кредит-ноты) модель заполняет свободно. В схеме
   они помечены как `derived`, и проверка по источнику к ним не применяется.

**Почему так.** Регулярка находит в счёте четыре даты, но не знает, какая из них дата выставления.
Это решает подпись рядом, а подписи у поставщиков разные: «Дата счёта», «от», «Date of issue»,
«Issued». Сопоставление требует понимания языка, поиск — нет. При этом модель **физически не
может выдумать значение**: она выбирает из списка, который составила не она.

У текстовых полей (названия сторон, условия оплаты, описания позиций) кандидатов нет: регулярками
их не собрать. Модель возвращает для них точную цитату, а система проверяет, что цитата есть в
документе.

Если нужного кандидата не нашлось (пробел в регулярках), модель может вернуть цитату и значение:
`{"quote": "1 234,56", "value": "1234.56"}`. Такой ответ проходит проверку привязки строже, чем
выбор кандидата (см. слой 2).

### Извлечение текста: почему не стандартный режим pdfplumber

В обычном режиме pdfplumber склеивает ячейки таблицы одиночным пробелом. Строка «количество 2,
цена 150 000,00» превращается в `2 150 000,00`, и количество сливается с ценой. В layout-режиме
крупный шрифт получает двойные пробелы между обычными словами. Поэтому текст собирается заново
из слов (`src/triage/pdf_text.py`): зазор шире 0.6 кегля шрифта считается колонкой (два
пробела), уже — обычным пробелом. Регулярки сумм считают разделителем тысяч только одиночный
пробел.

## Три слоя проверки

Каждое поле на выходе имеет статус `ok` или `flagged`, причём у флага всегда есть причина: слой,
код и сообщение.

### 1. Схема — `checks/schema_check.py`

Pydantic v2 проверяет типы, форматы и диапазоны, плюс несколько правил между полями.

| Что ловит | Пример |
|---|---|
| значение не того типа или формата | дата «15 янв», сумма с тремя знаками после запятой |
| битая контрольная сумма идентификатора | БИН, ИНН, IBAN (mod 97) с переставленными цифрами |
| корр. счёт вместо расчётного | ключ счёта не сходится с БИК: «this is the bank's correspondent account (к/с), not the settlement account (р/с)» |
| срок оплаты раньше даты счёта | в том числе когда модель перепутала эти две даты |
| отрицательная сумма не в кредит-ноте | |

### 2. Привязка к источнику — `checks/grounding.py`

- Выбранный id кандидата существует, и тип кандидата подходит полю. Если в `contract_number`
  стоит IBAN, поле помечается.
- Цитата для числа, даты или номера должна встречаться в тексте **точно** (после нормализации
  пробелов) и целым токеном. Кроме того, её нормализация должна давать то значение, которое
  заявила модель. Так ловится перестановка цифр: строка в документе есть, а значение ей не
  соответствует.
- Цитата для текстового поля может совпасть нечётко (rapidfuzz, порог 90): названия расходятся в
  кавычках, тире и регистре.
- Обязательное поле равно `null` — поле помечается, но это не ошибка обработки.
- Один напечатанный номер или одна дата назначены двум полям — помечаются оба.

**Почему для чисел только точное совпадение.** Сумма «12 345 678,90» с двумя переставленными
цифрами похожа на исходную примерно на 92%. Нечёткий порог 90 пропустил бы ровно ту ошибку,
ради которой этот слой существует. Цитата `234,56` внутри `1 234,56` тоже отвергается: обрезанное
число, которое случайно встречается в тексте, всё равно неверное.

### 3. Арифметика — `checks/arithmetic.py`

Проверяются три равенства с допуском в одну копейку на округление:
- количество × цена = сумма строки;
- сумма строк = subtotal (или total, или total − налог: цены бывают с НДС);
- subtotal + налог = total.

Этот слой ловит случай, когда все числа честно взяты из документа, но взяты не те: subtotal
вместо total, номер строки вместо количества. Если равенство не сходится, помечаются **все** его
участники: арифметика знает, что какое-то число неверно, но не знает какое.

### Проверено на демо (оракул + внедрённая ошибка)

| Ошибка модели | Кто поймал |
|---|---|
| выдуманный номер договора `ДГ-2026/017` (в счёте 06 договора нет) | привязка: «does not occur in the document» |
| в итоге 2,940.00 → 2904.00 (цитата верная) | привязка: «document says '2,940.00' = 2940.00, model claims 2904.00» и арифметика |
| к/с вместо р/с (счёт 04) | схема: ключ счёта по БИК |
| subtotal взят как total (счёт 13) | арифметика: subtotal + tax ≠ total |
| номер счёта взят как номер договора (счёт 02) | привязка: один кандидат на двух полях |
| IBAN взят как номер договора | привязка: тип кандидата не подходит |
| БИН покупателя взят как БИН поставщика (счёт 01) | привязка: одно значение на двух полях |

С правильным сопоставлением (оракул без ошибок) на всех 15 счетах **не срабатывает ни один флаг**,
то есть ложных срабатываний нет.

### Чего не ловит ни один слой

Это проверено, а не предположено:

- **Правильно оформленный, но чужой номер.** Номер заказа «3318», выданный за номер договора
  (счёт 06), проходит все три слоя: формат верный, нигде больше не используется, в арифметике не
  участвует.
- **Согласованная перестановка сторон.** Если модель поменяла местами поставщика и покупателя
  целиком (и названия, и налоговые номера), все значения взяты из документа, форматы верны,
  повторов нет.
- **Дата договора вместо даты счёта**, если срок оплаты всё равно позже неё.
- **Пропущенное необязательное поле.** Модель вернула `null` для срока оплаты, который в документе
  есть, — флага не будет.
- **Налог «в том числе»** без отдельно напечатанной суммы без НДС: ставку арифметика не проверяет.
- **Обрезанное описание позиции** («Аренда офиса» вместо «Аренда офиса 214, февраль»): цитата
  есть в документе.
- **Выводимые поля** (категория, признак кредит-ноты): проверки по источнику для них нет по
  определению.

Частично это закрывает политика риска: итог и реквизиты человек видит всегда. Остальное — материал
для замера: правки человека покажут, как часто такое случается на практике.

## Политика риска

Это отдельный конфиг, `config/risk_policy.toml`. Уровень риска поля — **бизнес-решение, а не
модельное**:

| Уровень | Поведение | Поля по умолчанию |
|---|---|---|
| `high` | всегда идёт на проверку человеку, даже без флагов | `total`, `supplier_account`, `supplier_bank_code` |
| `medium` | идёт на проверку, только если есть флаг | остальные |
| `low` | не показывается никогда, даже с флагом; флаги логируются для замера | `payment_terms`, `expense_category` |

Опечатка в имени поля в конфиге — ошибка при загрузке, а не молчаливое игнорирование.

## Схема счёта

15 полей шапки, позиции и 2 выводимых поля (`src/triage/schema.py`):

| Поле | Тип | Обяз. |
|---|---|---|
| supplier_name, buyer_name | текст (цитата) | да |
| supplier_tax_id, buyer_tax_id | БИН/ИИН, ИНН, VAT | поставщик |
| supplier_account | IBAN/ИИК или р/с | да |
| supplier_bank_code | BIC или БИК | |
| invoice_number | номер документа | да |
| contract_number | номер документа | **нет — часто отсутствует** |
| issue_date, due_date | дата | выставления |
| currency | ISO 4217 | да |
| subtotal, tax_amount, total | деньги | итого |
| payment_terms | текст (цитата) | |
| line_items[]: description, quantity, unit_price, amount | текст, число, деньги, деньги | да |
| expense_category, is_credit_note | derived | |

Номера договора в счёте часто нет, и наивная реализация («заполни схему») заставляет модель его
выдумать. В пяти синтетических счетах из 15 договора нет.

Банковские реквизиты в исходном списке полей отсутствовали, но политика риска на них ссылается,
поэтому они добавлены.

## Тестовые документы

`python -m synth.generate` создаёт 15 счетов (reportlab) и эталонную разметку `data/gold.json`.
Реальные счета не используются: в них чужие персональные и банковские данные.

- **5 макетов:** казахстанский «Счет на оплату» в стиле 1С; российский счёт с таблицей реквизитов;
  английский двухколоночный; английский компактный «метка: значение»; английский в немецкой
  верстке письма.
- **Разные подписи полей:** «Дата счёта», «от», «Дата выставления», «Invoice date», «Date of
  issue», «Issued».
- **Форматы дат:** `15.01.2026`, `15 Jan 2026`, `2026-01-15`, `January 15, 2026`, `«20» января 2026 г.`
- **Форматы чисел:** `1 234,56`, `1,234.56`, `1.234,56`.
- **Ловушки:** дата договора, отгрузки и периода услуг рядом с датой счёта; номера заказа,
  накладной, клиента, исходного счёта рядом с номером договора (или вместо него); НДС «в том
  числе»; «Без НДС»; кредит-нота с отрицательными суммами; р/с и к/с рядом.
- Все компании, банки и номера вымышлены, но **с верными контрольными суммами**: иначе проверка
  контрольных сумм не отличила бы ошибку модели от ошибки генератора.
- Эталон и PDF строятся из одних данных (`synth/specs.py`). Генерация детерминирована.
- `python -m synth.check_gold` проверяет эталон через тот же путь, что и пайплайн: каждое значение
  должно быть найдено в извлечённом тексте или среди кандидатов. Сейчас 15/15.

## Как запустить

Нужен Python 3.11+.

```bash
python -m venv .venv
```

```bash
. .venv/bin/activate
```

```bash
pip install -e ".[dev]"
```

**Без модели** — оракул сопоставляет по эталону, ошибки можно внедрить:

```bash
triage run data/invoices/inv_06_ru_marketing.pdf --oracle data/gold.json --inject "hallucinate:contract_number=ДГ-2026/017"
```

```bash
triage run data/invoices/inv_07_uk_software.pdf --oracle data/gold.json --inject transpose:total
```

```bash
triage run data/invoices/inv_04_ru_consulting.pdf --oracle data/gold.json --inject pick:supplier_account=I7
```

**С локальной моделью через Ollama** (или vLLM — меняется только `LLM_BASE_URL`):

```bash
ollama pull qwen3.5:9b
```

```bash
cp .env.example .env
```

```bash
set -a; . ./.env; set +a
```

```bash
triage run data/invoices/inv_06_ru_marketing.pdf
```

Модель, адрес и ключ берутся только из переменных окружения (`.env.example`), ключей в коде нет.
Формат ответа — `json_schema` (ограниченная генерация в OpenAI, vLLM и Ollama). Для провайдеров
без поддержки схемы есть `LLM_RESPONSE_FORMAT=json_object`. Если JSON невалиден, делается один
повтор с текстом ошибки.

**Отладка:**

```bash
triage candidates data/invoices/inv_13_de_software.pdf
```

```bash
triage candidates data/invoices/inv_13_de_software.pdf --annotated
```

```bash
triage run data/invoices/inv_01_kz_logistics.pdf --oracle data/gold.json --json
```

## Структура

```

src/triage/
  schema.py                    поля, их виды, Pydantic-модель счёта
  pdf_text.py                  PDF → текст (колонки отделены двумя пробелами)
  normalize.py                 подстрока → нормализованное значение (общая для поиска и проверки)
  idformats.py                 форматы и контрольные суммы идентификаторов
  candidates/                  поиск кандидатов: даты, суммы, идентификаторы, валюты
  llm/                         промпт, контракт ответа, клиент, оракул
  checks/                      три слоя проверки
  policy.py                    риск → показать человеку или нет
  pipeline.py, cli.py
synth/                         генератор счетов, эталон, проверка эталона
data/invoices/, data/gold.json 15 счетов и разметка
```

## Ограничения

Здесь честно перечислено, чего система не делает и что в ней не проверено:

- **Нет авторизации и пользователей.**
- **Только PDF с текстовым слоем**, OCR сканов нет. Скан даёт явную ошибку `NoTextLayerError`, а не
  пустой результат.
- **Только счета.** Акты, накладные, договоры не поддерживаются.
- **Нет дообучения**, модель используется как есть.
- **Нет очередей и фоновых воркеров:** документ обрабатывается синхронно.
- **Нет красивого дизайна.**
- **Только синтетические данные.** На реальных счетах качество не измерено. Синтетика честная
  (ловушки, разные макеты), но она порождена тем же автором, что и регулярки.
- **Регулярки покрывают форматы из синтетики** и соседние (KZ, RU, EU). Американские EIN,
  индийские GSTIN, суммы прописью, числа с апострофом (`1'234.56`) не поддерживаются.
- **Многостраничные счета** технически обрабатываются (страницы склеиваются), но не тестировались.
- **Перечень слабых мест проверок** — в разделе «Чего не ловит ни один слой».
- **Настоящая модель пока не прогонялась:** см. «Статус».
